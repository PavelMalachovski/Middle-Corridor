# Аккаунты, доступ, грузы в базе и события на чекпоинтах (этапы 1–2) — дизайн

Дата: 10.11.2026. Основа — `main` после PR #29 (санкции, восточный маршрут, блок «Груз»).
Сейчас реальных грузов нет: всё на моке, API открыт без ключа.

## Зачем
Экспедитор и его люди на узлах (Млада-Болеслав, Копер, Поти, Баку, Актау, Костанай, Румыния)
должны вести **реальные** грузы: создавать их, отмечать события на каждом чекпоинте, а все,
кто связан с грузом, — получать уведомления и видеть карточку. Видеть и менять груз может только
тот, кому экспедитор дал доступ. Это основа для этапа 3 (загрузка документов с распознаванием).

## Решения владельца
- Работа на узлах — **iOS-приложение** (сайт и Telegram — не сейчас).
- Вход — **приглашение + код на e-mail** (без паролей).
- **Груз принадлежит экспедитору**: он приглашает агентов на узлах (отмечают события своего узла)
  и клиентов (только смотрят). Владелец платформы — супер-админ.
- Уведомления — **push на iPhone и e-mail**.
- Порядок: этапы 1 (аккаунты и доступ) и 2 (грузы и события), документы — этап 3.
- **Компании заводит только владелец платформы** — и экспедиторов, и клиентов. Экспедитор
  приглашает людей в свою компанию и делится грузом с уже существующей компанией-клиентом.
- **Груз можно править с историей**: контейнер, описание, план отправления и ещё не пройденная
  часть маршрута; отмеченные события не трогаются, каждая правка — в журнале.
- **Агент указывает причину стоянки из списка** (погодный запрет, таможня, ожидание
  парома/судна, прочее) и «сняли со стоянки».
- **Пилот — несколько экспедиторов**, один человек может состоять в нескольких компаниях
  (список грузов — по всем, при создании груза — выбор компании).

## Цели, не-цели, анти-цели
**Цели:** компании, люди, роли, приглашения, вход по коду из письма, токены сессий; грузы
в Postgres с маршрутом и планом; события на чекпоинтах (ручные, с проверкой прав узла);
проекция положения/ETA/санкций/«Груза» из базы тем же `project_shipment`; подписки,
push и e-mail при событии; журнал действий; iOS: вход, мои грузы с сервера, создание груза,
«Отметить событие», регистрация push-токена.

**Не-цели (этапы 1–2):** загрузка и распознавание документов, фото штампа (этап 3 — вместе с
файлами), Android/сайт/Telegram для агентов, оплата и тарифы, SSO компаний, мультиязычные
письма сверх RU/EN.

**Анти-цели:**
- Реальный груз виден без входа (в открытом снимке, по номеру, в логах).
- Агент отмечает событие не своего узла или видит грузы чужого экспедитора.
- По ответу «код отправлен» можно понять, есть ли такой e-mail (перебор адресов).
- Токены и коды лежат в базе в открытом виде; токен в iOS — не в Keychain.
- Событие можно изменить или удалить без следа (только исправление новым событием + журнал).
- Push/e-mail раскрывает содержимое контейнера или санкционный статус на экране блокировки
  постороннего: в тексте — номер груза и событие, детали — после входа.

## Подходы
- **A. Свои аккаунты в нашем бэкенде (Postgres) + непрозрачные токены — выбран.** Полный
  контроль прав «по узлу», простая отзывка (удалил строку — сессии нет), без внешних
  зависимостей, кроме отправки писем. Минус — безопасность входа на нас (коды, лимиты, журнал).
- **B. Внешний провайдер (Auth0/Clerk/Supabase Auth).** Готовые коды и лимиты, но права «агент
  на узле Актау для грузов экспедитора X» всё равно наши; плюс зависимость, оплата за
  пользователей, данные людей у третьей стороны. Отброшено для пилота; можно перейти позже.
- **C. JWT без состояния.** Нельзя мгновенно отозвать доступ уволенного агента без чёрного
  списка — а это и есть состояние. Отброшено.

## Как устроено

### 1. Где живёт
Реальные данные — **только Railway** (FastAPI + Postgres, `MOCK_DATA=false`): там же бот и
планировщик. Если на Railway сейчас крутится демо на моке — аккаунтам заводится отдельный
сервис с собственной базой (решает исполнитель при деплое, проверив переменные). Vercel
остаётся публичным демо на моке и **не отдаёт** реальные грузы; эндпоинты аккаунтов при
`MOCK_DATA=true` отвечают `404`.

iOS — **два клиента**: карта, прогноз и демо-номера — как сейчас (Vercel); «Мои грузы»
аккаунта — с `MC_ACCOUNT_API_URL` (ключ сборки, Railway). Грузы аккаунта видны в списке и
карточке; на карте, в виджете и Live Activity — не на этом этапе. Локальные уведомления
(`NotificationRules.diff`) для грузов аккаунта выключены, когда устройство зарегистрировало
push-токен, — иначе дубль; без push (нет Apple Developer) работает локальный diff.

### 1а. Заведение компаний
Только платформа-админ: команда `python -m app.cli org create --kind forwarder|client --name …`
и `python -m app.cli invite --org … --email … --role owner` (Railway shell), плюс те же действия
через `POST /api/v1/admin/orgs`, `POST /api/v1/admin/orgs/{id}/invitations` для будущего экрана.
Первый платформа-админ — `python -m app.cli admin --email …` (флаг `is_platform_admin`, вход —
обычным кодом). Экспедитор при «Поделиться» выбирает компанию-клиента из списка, который ему
открыл админ (`org_links`: forwarder_id, client_id) — чужие клиенты не видны.

### 2. Модель данных (новые таблицы, миграция Alembic)
- `organizations` — id, name, kind (`forwarder` | `client` | `platform`), created_at.
- `users` — id, email (уникальный, в нижнем регистре), name, locale (`ru`/`en`), is_platform_admin,
  created_at, last_login_at, disabled_at.
- `memberships` — user_id, org_id, role (`owner` | `admin` | `agent` | `viewer`),
  node_codes (массив кодов узлов, только для `agent`; пусто — все узлы маршрута груза).
- `invitations` — id, org_id, email, role, node_codes, code_hash, invited_by, expires_at (7 дней),
  accepted_at, revoked_at.
- `login_codes` — id, email, code_hash, expires_at (10 мин), attempts, used_at.
- `sessions` — id, user_id, token_hash, created_at, last_used_at, expires_at (60 дней),
  device_name, revoked_at.
- `shipments` — id, ref (уникальный, «MC-27-0001»), org_id (владелец-экспедитор),
  container_no, container_type, route (массив кодов узлов из `corridor.NODES`),
  planned_departure_at, cargo (текст), cargo_manifest (JSON, как `CargoManifest`), created_by,
  created_at, archived_at.
- `shipment_shares` — shipment_id, org_id (клиент) — кто ещё видит груз (только чтение).
- `org_links` — forwarder_id, client_id: с какими клиентами экспедитору разрешено делиться.
- `shipment_events` — id, shipment_id, kind (`arrived` | `departed` | `held` | `released`),
  node_code, occurred_at, hold_code (для `held`: `weather_ban` | `customs_wait` | `ferry_loading_wait` |
  `other` — существующие коды `hold_code` проекции, подписи уже есть в вебе и iOS), note, vessel, source
  (`manual`), created_by, created_at, supersedes_id (исправление ссылается на ошибочное;
  удалений нет).
- `shipment_revisions` — id, shipment_id, changed_by, at, before/after (JSON изменённых полей).
  Правка маршрута — только узлов после последнего отмеченного события; новый маршрут проходит ту
  же проверку плеч.
- `subscriptions` — user_id, shipment_id, channels (push, email), muted_at.
- `devices` — user_id, apns_token, environment (sandbox/production), created_at, revoked_at.
- `audit_log` — id, user_id, action, entity, entity_id, at, ip, details (JSON без персональных
  данных сверх необходимого).

Enum'ы — VARCHAR (`native_enum=False`), как во всём проекте.

### 3. Права (единственная функция проверки, вызывается на каждом запросе)
| Роль | Видит | Может |
|---|---|---|
| платформа-админ | всё | всё + компании, связи экспедитор–клиент, отзыв пользователей |
| `owner`/`admin` экспедитора | все грузы своей компании | создать/править/архивировать груз, приглашать в свою компанию, делиться со связанным клиентом, отмечать события любых узлов |
| `agent` экспедитора | грузы компании, в маршруте которых есть его узел | отмечать события **только своих узлов** |
| `viewer` компании-клиента | грузы, которыми с его компанией поделились | только смотреть, подписываться |

Нет доступа — `404`, а не `403` (не раскрываем, что груз существует).

### 4. Вход
1. `POST /api/v1/auth/code {email}` — всегда `202` (нет перебора адресов). Если e-mail есть
   среди пользователей или неистёкших приглашений — письмо с 6-значным кодом; код хранится как
   HMAC-SHA256 с серверным секретом. Лимиты: 3 письма за 15 мин на адрес, 20 за час на IP.
2. `POST /api/v1/auth/verify {email, code, device_name}` — до 5 попыток на код; при успехе
   принимаются висящие приглашения на этот e-mail (создаются user и memberships) и выдаётся
   токен сессии (32 байта, base64url, в базе — SHA-256). Ответ: токен + профиль.
3. Дальше `Authorization: Bearer <токен>`; `POST /api/v1/auth/logout` отзывает сессию.
   `GET /api/v1/me` — профиль, компании, роли.
Приглашение: `POST /api/v1/orgs/{id}/invitations {email, role, node_codes}` (owner/admin) →
письмо «вас пригласили… войдите в приложении с этим e-mail». Ссылок-токенов нет: на бесплатном
и даже платном аккаунте Universal Links требуют настройки домена — код из письма проще.

### 5. Грузы и события
- `GET /api/v1/my/shipments` — доступные грузы в формате `Shipment` (тот же
  `project_shipment`: проекция, ETA, «Груз», санкции, если есть пакинг-лист — на этапе 3).
- `POST /api/v1/my/shipments` (owner/admin) — ref выдаётся сервером; контейнер — проверка
  ISO 6346 (контрольная цифра); маршрут — список узлов, каждая пара должна быть плечом коридора;
  план — от `planned_departure_at` по типичным временам плеч (как `build_plan`).
- `GET /api/v1/my/shipments/{ref}`; `PATCH …/{ref}` (правка с записью в `shipment_revisions`);
  `POST …/{ref}/share {org_id}`; `POST …/{ref}/archive`. При нескольких компаниях-экспедиторах
  у человека `POST` создания принимает `org_id`.
- `POST /api/v1/my/shipments/{ref}/events {kind, node_code, occurred_at?, hold_code?, note?,
  vessel?, supersedes_id?}` — `held` требует `hold_code`, `released` — открытой стоянки на
  этом узле; узел должен быть в маршруте и в правах агента; время не в будущем и не
  раньше предыдущего события того же груза (иначе 422 с понятной причиной). Событие сразу
  меняет проекцию (`ShipmentPlan.events`).
- **Источник для проекции** — `DbShipmentSource` реализует существующий Protocol
  `ShipmentSource`; публичный `/api/v1/snapshot` его **не использует**.

### 6. Уведомления
При событии — всем подписчикам груза (по умолчанию подписаны все, у кого есть доступ),
кроме автора: push (APNs, HTTP/2, ключ .p8) и e-mail. Текст: «MC-27-0001: прибыл в Актау» /
«…: убыл из Поти» / «…: стоит в Актау — погодный запрет» / «…: снят со стоянки». Правка груза
уведомлений не шлёт (кроме смены маршрута). Отправка — фоновая задача с повтором; провайдеры за Protocol
(`PushSender`, `EmailSender`): в разработке и тестах — запись в лог; боевые включаются ключами
в ENV. Без ключей APNs (нет Apple Developer) push просто не уходит, e-mail работает.
`POST /api/v1/me/devices {apns_token, environment}` — регистрация устройства.

### 7. iOS
- Настройки → «Войти»: e-mail → код → готово; токен — Keychain; «Выйти».
- После входа «Мои грузы» показывает серверные грузы аккаунта (секции по срочности, как сейчас);
  отслеживание демо-номеров по ссылке остаётся для гостя.
- Экспедитор: «+» → «Новый груз»: контейнер (с проверкой), маршрут (пресеты «Европа →
  Казахстан», «Китай → Европа» и ручной выбор узлов), план отправления, описание.
- Экспедитор в нескольких компаниях — выбор компании при создании; список — по всем.
- Карточка: кнопка **«Отметить событие»** (видна, если есть право): узел (только доступные),
  прибыл / убыл / стоит (причина из списка) / снят со стоянки, время (по умолчанию сейчас),
  судно (для морских плеч), примечание. Owner/admin — ещё «Изменить груз».
- Push: запрос разрешения после входа, регистрация токена; нажатие открывает груз.
- Приглашение людей (owner/admin): экран компании — e-mail, роль, узлы агента. Компании
  создаёт платформа-админ (CLI/админ-API; экрана админа в iOS на этом этапе нет).

### 8. Безопасность (с первого этапа)
Проверка прав на сервере в каждом обработчике (функция из п. 3 + тесты на каждую роль);
секреты только в ENV; коды и токены — хэши; сравнение — `hmac.compare_digest`; лимиты по адресу
и IP (счётчики в Postgres — переживают перезапуск); журнал всех изменений; CORS — только сайт;
размер тел запросов ограничен; в логах — id, не e-mail; HTTPS (Railway); на iOS — Keychain,
без логирования токена. Перед реальными клиентами — этап 4 (аудит).

## Тесты
pytest на SQLite/Postgres: вход (лимиты, попытки, истечение, «нет такого e-mail» → тот же 202),
права (матрица ролей × действий, агент чужого узла → 404/422), события (порядок времени, узел
вне маршрута, исправление), уведомления (кто получает, автор — нет, фейковые отправители),
проекция из базы, публичный снимок не содержит реальных грузов. `swift test`: модели, Keychain-
хранилище за протоколом, клиент с токеном. UI-смоук: вход и «Отметить событие» на фейковом API.
CI Postgres: миграция туда-обратно и `alembic check`.

Формат ref (`MC-YY-NNNN` с годом создания), тексты писем, точные лимиты в пределах указанных,
вид экранов iOS по существующим токенам, выбор библиотеки APNs (или прямой HTTP/2 через httpx).
