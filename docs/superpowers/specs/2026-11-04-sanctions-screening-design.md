# Проверка грузов на санкции: коды ТН ВЭД из пакинг-листа × санкционные списки — дизайн

Дата: 04.11.2026. Основа — `main` после PR #25: мок-бэкенд (`MOCK_DATA`), демо-сервер на
Vercel как сервер iOS по умолчанию, локальные уведомления iOS (`NotificationRules`).

## Зачем

Владелец хочет узнавать **до того, как поезд придёт в Актау**, что в контейнере, возможно,
санкционный товар: «по списку такому-то похоже, что тут что-то не то». Это подсказка для
ручной проверки, а не вердикт. Между Хоргосом и Актау у владельца есть время что-то
сделать: запросить документы, предупредить клиента, не грузить на паром.

## Решения владельца

- **Списки:** CHPL (Common High Priority List, общий список ЕС/США/UK/Японии) и
  регламент ЕС 833/2014.
- **Источник пакинг-листов:** пока **только демо-данные в моке**. Загрузка через бота или
  API — не сейчас: боевого источника отправок в проекте нет вообще.
- **Где предупреждение:** **только iOS** — уведомление и блок в карточке груза. В
  публичный Telegram-канал не идёт никогда.
- **Когда:** проверка **сразу, как пришёл пакинг-лист**. Если груз прошёл Хоргос /
  Алтынколь, а листа так и нет — отдельное предупреждение «проверить нельзя».
- **Строгость:** уведомление — только когда **код из списка И связь с РФ/РБ в листе**
  (происхождение — для запретов ввоза, получатель или страна назначения — для запретов
  экспорта). Совпадение по одному коду видно в карточке как «проверить вручную», но без
  уведомления. Причина: поезд идёт на запад, и по одному коду под флаг попала бы почти вся
  китайская электроника и сталь.
- **Подход:** проверка на сервере, результат — блок `sanctions` в ответе
  `/api/v1/shipments/{ref}` (см. «Подходы»).

## Цели, не-цели, анти-цели

**Цели:** списки CHPL и ЕС 833/2014 как файлы данных с источником и датой; пакинг-листы у
демо-грузов; проверка на сервере со статусом и совпадениями; поле в API; в iOS —
уведомление, переключатель в настройках, блок в карточке, пометка в списке грузов; RU/EN;
тесты pytest и `swift test`; проверка в симуляторе против мока.

**Не-цели:** загрузка пакинг-листов (бот, API, файлы); показ на сайте и в боте; проверка
по спискам лиц (SDN, Entity List, санкционные списки компаний) — только товары по кодам;
юридическое заключение; автоматическое обновление списков; виджет и Live Activity;
доступ к пакинг-листам по ключу (понадобится с боевыми данными).

**Анти-цели — провал, даже если «работает»:**
- Флаг выглядит как вердикт («санкционный груз»). Везде «возможно» и «проверьте вручную».
- В списках коды «по памяти»: каждая запись переписана из официального текста, у списка
  есть ссылка на источник и дата «актуально на». Запись, которую не удалось подтвердить по
  источнику, в файл не попадает.
- Шум: баннер на каждый контейнер с электроникой или металлом.
- Пакинг-лист целиком в публичном ответе API (номер груза знает кто угодно).
- Одно и то же предупреждение приходит повторно (при каждом обновлении или перезапуске).
- «Пакинг-листа нет» показано как «чисто».

## Как устроено

### 1. Санкционные списки — файлы данных

Каталог `app/data/sanctions/` (новый):

- `chpl.csv` — CHPL целиком: около 50 позиций по 6-значным кодам HS, с уровнем (Tier).
- `eu_833_2014.csv` — запреты ЕС из регламента 833/2014, **у которых есть коды КН/HS**.
  Для этого маршрута (на запад, в ЕС) важны **запреты ввоза товаров российского
  происхождения**: приложения XVII (чугун и сталь) и XXI. Приложения без кодов
  (например, VII — по контрольным спискам) не берём: сверять по ТН ВЭД их нельзя.
  *Решение исполнителя дизайна; владелец может поправить.*
- Метаданные списков (код списка, название RU/EN, ссылка на источник, «актуально на») —
  рядом с CSV, формат на выбор исполнителя.

Колонки записи: `code` (4–8 цифр, без точек и пробелов), `item_ru`, `item_en`, `ref`
(Tier для CHPL, номер приложения для ЕС), `measure` (`export_ban` | `import_ban`),
`countries` (страны, связь с которыми делает совпадение сильным: `RU,BY` для CHPL — он
действует и по России, и по Беларуси; `RU` для 833/2014 — он про Россию, Беларусь
регулирует отдельный регламент 765/2006, его не берём).

Содержимое — **только из официальных текстов**: страница CHPL Еврокомиссии,
консолидированная редакция 833/2014 на EUR-Lex. Исполнитель указывает дату консолидации.
Проверить, что CHPL в 833/2014 — это приложение XL; если так, записать это в `ref`.
Обновляет списки человек (как пороги ветра), через PR.

Тест проверяет файлы: коды — только цифры длиной 4–8, `measure` и `countries` из
допустимых значений, у каждого списка есть источник и дата.

**Vercel:** демо-сервер работает функцией на Vercel. Исполнитель проверяет, что CSV
попадают в сборку функции: после деплоя превью `/api/v1/shipments/<флаженный груз>`
отдаёт статус. Если не попадают — `functions.includeFiles` в `vercel.json`.

### 2. Пакинг-лист — модель и демо-данные

Внутренняя модель (в API целиком не уходит), поле `ShipmentPlan.packing_list: PackingList | None`:

- `received_at: datetime` — когда лист пришёл;
- `consignee_country: str | None`, `destination_country: str | None` — ISO-2;
- `lines`: `no`, `hs_code` (10 цифр ТН ВЭД ЕАЭС), `description`, `description_en`,
  `origin_country: str | None` (ISO-2).

`received_at` в моке — относительно `at`, как и все события мока
(`MockShipmentSource.list_plans` строит план от `now = at or clock()`). Поэтому статус
демо-груза в replay не меняется — так же, как его положение. Правило «при `at <
received_at` листа ещё нет» живёт в `services/sanctions.py` и проверяется тестом на
собранном вручную плане. *Уточнено после проверки дизайна.*

Демо-грузы (у всех маршрут через Хоргос):

| Груз | Где сейчас | Пакинг-лист | Ожидаемый статус |
|---|---|---|---|
| MC-26-0431 | Казахстан, Кызылорда → Бейнеу, до Актау | есть; среди позиций — стальной прокат по коду из приложения XVII, происхождение RU | `flagged`, уведомление |
| MC-26-0412 | на пароме по Каспию | электроника, код из CHPL, происхождение CN, получатель HU | `review`, без уведомления |
| MC-26-0447 | только что прошёл Хоргос | нет | `missing`, уведомление |
| MC-26-0455 | ещё в Китае | нет | `pending` |
| остальные, включая историю 0398 | — | чистые листы | `clear` |

Коды в демо-листах — из реальных записей файлов списков (тест это проверяет).
Историю 0398 (`story.py`) не меняем, кроме чистого пакинг-листа.

### 3. Проверка — `app/services/sanctions.py`

Функция без внешних зависимостей (не импортирует FastAPI/aiogram), на вход — план груза,
списки и момент `at`.

**Сопоставление кодов.** Коды нормализуются до цифр. Код списка из 4–6 цифр сравнивается
с началом 10-значного кода ТН ВЭД. Код из 8 цифр (КН ЕС) сравнивается **по первым 6
цифрам**: первые 6 цифр гармонизированы во всём мире, а 7–10 знаки ТН ВЭД ЕАЭС и КН ЕС
могут не совпадать. В совпадении сохраняется исходный код списка, чтобы человек сверил
сам.

**Сила совпадения.**
- `import_ban`: сильное, если происхождение позиции входит в `countries`.
- `export_ban`: сильное, если страна получателя или страна назначения входит в `countries`.
- Иначе слабое. Если нужной страны в листе нет, это слабое совпадение с причиной
  «происхождение не указано» или «получатель не указан».

**Статус** (код для интерфейса):
- `pending` — листа нет, граница Казахстана впереди (или маршрут без Хоргоса);
- `missing` — листа нет, а контрольная точка `KHORGOS` пройдена;
- `clear` — лист есть, совпадений нет;
- `review` — только слабые совпадения;
- `flagged` — есть хотя бы одно сильное.

«Хоргос пройден» — по состоянию контрольной точки `KHORGOS` в уже существующих
`checkpoints` груза.

### 4. API

`Shipment.sanctions: SanctionsCheck | None` в ответе `/api/v1/shipments/{ref}` и в
снимке. Поля:

- `status` — код из списка выше;
- `checked_at` — время пакинг-листа или `null`;
- `lists` — какие списки применялись: `code`, `name`, `name_en`, `as_of`;
- `matches` — **только совпавшие позиции**: `line_no`, `hs_code`, `description`,
  `description_en`, `origin_country`, `list_id` (какой список), `list_code` (исходный код из списка),
  `ref` (Tier или приложение), `measure`, `strong`, `reason_code`
  (`origin_ru`, `consignee_ru`, `code_only`, `no_origin`, `no_consignee`).

Русские строки идут вместе с кодами (правило CLAUDE.md). Остальные позиции листа в ответ
не попадают. Без пакинг-листов (боевой режим сейчас) — `null`.

### 5. iOS

- **MCCore, модели:** `SanctionsCheck` и вложенные типы, необязательное поле
  `Shipment.sanctions` (старый бэкенд — `nil`), даты — через `APIDate.parse`. Обновить
  фикстуры (`ios/scripts/patch_fixtures.py` или перезапись из мока): одна с `flagged`,
  одна с `review`.
- **`NotificationRules`:** новый вид `NoticeKind.sanctions` и
  `NotifySettings.sanctions` (по умолчанию включён). В отличие от остальных видов,
  уведомление о санкциях считается **по текущему состоянию, а не по разнице «было →
  стало»**: каждый груз со статусом `flagged` или `missing` даёт уведомление с
  детерминированным `id` (груз + статус + отсортированные коды сильных совпадений), и
  оно уходит, только если такого `id` ещё нет в **сохранённом наборе отправленных**.
  Набор хранит приложение (`UserDefaults`, рядом с `NotifyPrefs`). Чистая функция в
  MCCore получает набор на вход, `AppModel` после отправки дописывает в него `id`.
  Так флаг не пропускается и не повторяется: груз добавили уже `flagged` — уведомление
  есть; перезапуск, смена сервера, потеря кэша — повтора нет; новое сильное совпадение —
  новый `id`, новое уведомление. Остальные виды уведомлений остаются на разнице, как
  сейчас.
  **Добавление груза:** `TrackedShipments.add()` не вызывает `onChange`, поэтому
  `AppModel` после успешного добавления сразу прогоняет правило санкций для этого груза,
  не дожидаясь обновления по таймеру. В `merge` санкции — самый высокий приоритет, выше
  шторма. *Уточнено после проверки дизайна: `Notifier` отправленное не запоминает,
  одинаковый `id` повтор не останавливает.*
- **Тексты (RU; EN — аналогично):**
  - `flagged`: «MC-26-0431: возможна санкционка» / «По списку ЕС 833/2014 (прил. XVII):
    поз. 3, код 7208 51…, происхождение RU. Проверьте вручную.» Если сильных совпадений
    несколько — первое плюс «и ещё N».
  - `missing`: «MC-26-0447: прошёл границу Казахстана без пакинг-листа» / «Проверить на
    санкции нельзя — запросите пакинг-лист до Актау.»
- **Настройки:** переключатель «Санкционные риски» рядом с остальными видами
  уведомлений (`accessibilityIdentifier` `notify.sanctions`).
- **Карточка груза:** блок «Проверка санкций» в стиле остальных блоков: статус;
  совпадения (сильные первыми, цветом риска; слабые — нейтрально, «совпал код, связи с
  РФ/РБ в листе нет»); какие списки и «актуально на»; строка «Это подсказка, а не
  юридическое заключение». При `pending` — «Ждём пакинг-лист», при `clear` — коротко
  «Совпадений нет».
- **Список грузов:** при `flagged`/`missing` — красная пометка «Санкции?» в строке, груз
  попадает в группу `attention`.
- Локализация RU/EN в `Localizable.xcstrings` и `Labels`/`Strings`.

## Подходы

- **A. Проверка на сервере, результат в ответе о грузе — выбран.** Списки и логика в
  одном месте, iOS уже раз в минуту запрашивает каждый груз, уведомление встаёт в
  `NotificationRules` без новых запросов. Сайт и бот смогут показать то же поле позже.
- **B. Сервер, отдельный запрос `/shipments/{ref}/sanctions`.** Данные о содержимом
  отделены от карточки, но iOS делает лишний запрос на груз каждую минуту, а данные для
  уведомлений лежат в двух местах. Отделение не защищает: оба адреса публичные по номеру.
- **C. Сверка в приложении iOS, списки вшиты.** Отброшен: список обновляется только
  новой версией приложения, логику пришлось бы дублировать для сайта.

## Тесты

- **pytest:** сопоставление (префикс 6, КН-8 по 6 знакам, 4-значные коды); сила по
  `countries` для обоих видов мер; все пять статусов; `at` раньше `received_at` на
  собранном вручную плане → листа нет; проверка файлов списков; ожидаемые статусы демо-грузов из таблицы;
  в ответе API нет позиций листа, кроме совпавших.
- **`swift test`:** декодирование (с полем и без); правила уведомлений: `flagged` без
  записи в наборе отправленных → уведомление; тот же `id` уже в наборе → тишина (в том
  числе без прошлого состояния: смена сервера, пустой кэш); новое сильное совпадение →
  новое уведомление; `review` → тишина; `missing` → уведомление; переключатель выключен
  → тишина; в `merge` санкции сверху.
- **UI-смоук:** карточка с блоком на фикстуре `-mc-fake-api`, скриншот.
- **Симулятор против мока:** добавить MC-26-0431 → баннер «возможна санкционка»;
  MC-26-0412 → блок «проверить вручную» без баннера.
